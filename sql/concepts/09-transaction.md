## 1. 트랜잭션의 개념과 ACID

**트랜잭션(Transaction)**은 데이터베이스에서 **하나의 논리적인 작업 단위**로 처리하는 연산들의 묶음이다. 여러 SQL문으로 이루어져도 업무상 하나의 작업이라면 **모두 성공하거나, 문제가 있을 때 모두 취소**되도록 관리해야 한다.

예를 들어 A 계좌에서 B 계좌로 10,000원을 이체할 때는 **A 계좌 출금과 B 계좌 입금이 함께 완료**되어야 한다. 한쪽만 반영되면 잔액의 일관성이 깨지기 때문이다.

트랜잭션의 신뢰성을 설명하는 네 가지 특성을 **ACID**라고 한다.

| 특성                    | 핵심 의미                                                          | 이체 예시                                          |
| ----------------------- | ------------------------------------------------------------------ | -------------------------------------------------- |
| **원자성(Atomicity)**   | 작업 전체가 하나처럼 성공하거나 취소되어야 함 (**All or Nothing**) | 출금만 반영되는 상태를 남기지 않음                 |
| **일관성(Consistency)** | 작업 전후에 데이터의 무결성·업무 규칙을 지켜야 함                  | 이체 후에도 잔액 관련 규칙을 만족                  |
| **격리성(Isolation)**   | 동시 트랜잭션 사이의 간섭을 정해진 수준으로 제어                   | 다른 거래가 미확정 이체 내역을 잘못 읽지 않도록 함 |
| **지속성(Durability)**  | `COMMIT`된 결과가 장애 후에도 복구 가능하도록 보장됨               | 이체 완료 후 재시작해도 결과 유지                  |

**원자성**은 작업의 완전한 성공 or 취소, **격리성**은 동시 실행 시의 간섭 제어, **지속성**은 확정된 결과의 보장을 뜻한다. 일관성을 지키려면 데이터베이스의 제약조건뿐 아니라 애플리케이션의 업무 규칙도 올바르게 구현해야 한다.

## 2. 트랜잭션 격리 수준과 읽기 문제

**격리 수준(Isolation Level)**은 여러 트랜잭션이 동시에 실행될 때 **다른 트랜잭션의 변경을 어디까지 볼 수 있는지** 정하는 기준이다. 격리 수준을 이해하려면 대표적인 세 가지 읽기 문제를 구분해야 한다.

| 읽기 문제               | 의미                                                          | 상황 예시                                                     |
| ----------------------- | ------------------------------------------------------------- | ------------------------------------------------------------- |
| **Dirty Read**          | 다른 트랜잭션이 **아직 COMMIT하지 않은 값**을 읽음            | A가 급여를 수정했지만 취소했는데, B가 취소 전 값을 읽음       |
| **Non-Repeatable Read** | 한 트랜잭션에서 **같은 행을 두 번 읽었는데 값이 달라짐**      | B가 중간에 값을 수정·COMMIT하여 A의 두 조회 결과가 다름       |
| **Phantom Read**        | 같은 조건으로 재조회했는데 **조건에 맞는 행의 집합이 달라짐** | B가 조건에 맞는 직원을 추가·COMMIT하여 A의 재조회 건수가 증가 |

**Non-Repeatable Read는 기존 행의 값 변화**, **Phantom Read는 조건을 만족하는 행 집합의 변화**에 초점을 맞추면 구별하기 쉽다.

### SQL 표준의 네 가지 격리 수준

| 격리 수준          | Dirty Read | Non-Repeatable Read | Phantom Read |
| ------------------ | ---------- | ------------------- | ------------ |
| `READ UNCOMMITTED` | 가능       | 가능                | 가능         |
| `READ COMMITTED`   | 방지       | 가능                | 가능         |
| `REPEATABLE READ`  | 방지       | 방지                | 가능         |
| `SERIALIZABLE`     | 방지       | 방지                | 방지         |

격리 수준이 높을수록 일반적으로 더 강한 일관성을 제공하지만, 동시성 처리와 충돌 가능성까지 고려해야 한다.

### 트랜잭션 격리 수준의 4가지 종류

**1. READ UNCOMMITTED (커밋되지 않은 읽기)**

- 다른 트랜잭션이 **COMMIT하지 않은 데이터까지 읽을 수 있는** 가장 낮은 격리 수준이다.
- Dirty Read, Non-Repeatable Read, Phantom Read가 모두 발생할 수 있다.

**2. READ COMMITTED (커밋된 읽기)**

- 다른 트랜잭션이 **COMMIT한 데이터만 읽을 수 있는** 격리 수준이다.
- Dirty Read는 방지하지만, 같은 데이터를 다시 조회했을 때 결과가 달라질 수 있다.
- **Oracle의 기본 격리 수준**이다.

**3. REPEATABLE READ (반복 가능한 읽기)**

- 하나의 트랜잭션에서 **이미 읽은 행을 다시 조회해도 같은 값을 보장**하는 격리 수준이다.
- Dirty Read와 Non-Repeatable Read는 방지하지만, Phantom Read는 발생할 수 있다.

**4. SERIALIZABLE (직렬화 가능)**

- 여러 트랜잭션이 동시에 실행되더라도 **순차적으로 실행한 것과 같은 결과를 보장**하는 가장 높은 격리 수준이다.
- 세 가지 읽기 문제를 모두 방지하지만, 동시 실행 시 충돌이나 재시도가 필요할 수 있다.

**참고:** Oracle은 `READ COMMITTED`, `SERIALIZABLE` 격리 수준과 `READ ONLY` 트랜잭션 모드를 지원한다.

## 3. 명시적인 트랜잭션 제어 명령어

**명시적 트랜잭션 제어**는 사용자가 TCL(Transaction Control Language) 명령어를 직접 실행해 변경 내용을 확정하거나 취소하는 것이다. Oracle에서는 일반적으로 첫 DML로 데이터 변경 트랜잭션이 시작되며, `COMMIT` 또는 전체 `ROLLBACK`으로 종료된다.

| 명령어             | 역할                                                  |
| ------------------ | ----------------------------------------------------- |
| `COMMIT`           | 아직 확정하지 않은 변경을 확정하고 트랜잭션 종료      |
| `ROLLBACK`         | 아직 확정하지 않은 변경 전체를 취소하고 트랜잭션 종료 |
| `SAVEPOINT 이름`   | 트랜잭션 중간에 되돌아갈 지점 지정                    |
| `ROLLBACK TO 이름` | 저장점 이후의 변경만 취소하고 **트랜잭션은 유지**     |

`ROLLBACK TO SAVEPOINT 이름`도 같은 의미다. `COMMIT`이나 전체 `ROLLBACK`을 실행하면 해당 트랜잭션의 저장점도 사라진다.

<br>

## 4. 암시적인 트랜잭션 제어

**암시적 트랜잭션 제어**는 사용자가 `COMMIT`이나 `ROLLBACK`을 직접 입력하지 않아도 **SQL 명령 또는 세션 종료 상황에 따라 트랜잭션이 자동으로 처리**되는 것이다.

| 상황                                           | 자동 처리                  | 알아둘 점                                                  |
| ---------------------------------------------- | -------------------------- | ---------------------------------------------------------- |
| `CREATE`, `ALTER`, `DROP`, `TRUNCATE` 등의 DDL | 암묵적 `COMMIT`            | Oracle은 **DDL 실행 전**, 그리고 **성공 후**에도 확정한다. |
| `GRANT`, `REVOKE` 등의 DCL                     | 암묵적 `COMMIT`            | 미확정 DML 변경이 함께 확정될 수 있다.                     |
| SQL\*Plus의 정상 종료                          | 기본적으로 `COMMIT`        | 다른 클라이언트는 종료·자동 커밋 설정에 따라 다를 수 있다. |
| 세션의 비정상 종료·시스템 장애                 | 미확정 트랜잭션 `ROLLBACK` | 이미 `COMMIT`한 변경은 취소되지 않는다.                    |

예를 들어 `UPDATE` 후 아직 `COMMIT`하지 않았더라도 `CREATE TABLE`을 실행하면 **앞선 `UPDATE`가 확정**될 수 있다.

<br>

## 5. COMMIT과 ROLLBACK 전후의 데이터 상태

데이터를 수정하고 **확정하기 전에는 자신의 세션에서 변경 결과를 볼 수 있지만, 다른 세션은 미확정 내용을 볼 수 없다.**

Oracle에서는 일반 `SELECT`가 이전에 확정된 버전을 읽을 수 있으며, 동일한 행에 대한 충돌하는 `UPDATE` 등은 잠금 때문에 대기할 수 있다.

| 시점                 | 내 세션에서 보이는 값 | 다른 세션에서 보이는 값 (`READ COMMITTED` 기준) | 변경 행의 잠금 |
| -------------------- | --------------------- | ----------------------------------------------- | -------------- |
| **COMMIT 전**        | 내가 수정한 값        | 마지막으로 확정된 이전 값                       | 유지           |
| **COMMIT 후**        | 확정한 값             | 새로 시작한 조회부터 확정한 값 확인 가능        | 해제           |
| **전체 ROLLBACK 후** | 수정 전 값으로 복귀   | 취소된 값은 보이지 않음                         | 해제           |

`COMMIT`된 결과는 **일반 `ROLLBACK`으로 되돌릴 수 없다.**

### 값의 변화를 확인하는 예제

(자동 커밋(Auto-commit)을 비활성화한 상태로 실행)

```sql
CREATE TABLE TX_TEST (
    ID     NUMBER PRIMARY KEY,
    AMOUNT NUMBER NOT NULL
);

INSERT INTO TX_TEST (ID, AMOUNT) VALUES (1, 100);
COMMIT;  -- 시작 값 확정: 100

UPDATE TX_TEST SET AMOUNT = 150 WHERE ID = 1;
SELECT AMOUNT FROM TX_TEST WHERE ID = 1;
-- 내 세션: 150 / 다른 세션: 아직 100

COMMIT;
-- 다른 세션도 이후 새 조회에서는 150 확인 가능

UPDATE TX_TEST SET AMOUNT = 180 WHERE ID = 1;
ROLLBACK;
SELECT AMOUNT FROM TX_TEST WHERE ID = 1;
-- 결과: 150 (마지막 COMMIT 상태로 복귀)
```

<br>

### SAVEPOINT 실습

앞의 `TX_TEST`에 1번 행(`AMOUNT = 150`)이 확정된 상태에서 이어서 실행하는 예제다.

```sql
INSERT INTO TX_TEST (ID, AMOUNT) VALUES (2, 200);
SAVEPOINT SP1;

INSERT INTO TX_TEST (ID, AMOUNT) VALUES (3, 300);
ROLLBACK TO SP1;  -- 3번 행만 취소

SELECT ID, AMOUNT FROM TX_TEST ORDER BY ID;
-- 결과: (1, 150), (2, 200)

ROLLBACK;  -- 이번 트랜잭션에서 추가한 2번 행도 취소
SELECT ID, AMOUNT FROM TX_TEST ORDER BY ID;
-- 결과: (1, 150)
```
